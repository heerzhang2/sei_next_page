## 问题1: 为什么 #html 会变成 #rsc？

**根本原因**：Cache API **不支持 URL fragment（#）作为缓存键的区分**！

当你存储：

- `https://example.com/page#html`
- `https://example.com/page#rsc`


Cache API 会**忽略 fragment 部分**，把它们当作**同一个键**！所以第二次 `cache.put()` 会覆盖第一次的内容。这就是为什么 `#html` 被 `#rsc` 覆盖的原因。

**解决方案**：使用**查询参数**而不是 fragment 来区分 HTML 和 RSC。

## 问题2: 为什么需要自定义处理 CACHE_URLS？

Serwist 的内置消息处理只针对 **precache manifest**（`__SW_MANIFEST`），不支持：

1. 运行时动态缓存用户指定的 URLs
2. 同时缓存 HTML 和 RSC 两个版本
3. 自定义缓存键标准化
4. 错误处理和进度报告


所以必须自定义代码来实现这些功能。

## 问题3: SPA vs Next.js PWA

**是的！SPA 的 PWA 实现简单得多**：

- ✓ 只有一个版本的页面（HTML + JS）
- ✓ 不需要区分 HTML 和 RSC
- ✓ 缓存策略简单直接
- ✓ 没有服务端渲染的复杂性


Next.js RSC 增加了复杂度，因为需要管理两个版本的页面和它们之间的关系。

Chrome Cache Storage 限制详解
全局共享限制
6% 的磁盘空间：是所有网站 Cache Storage 的总容量

共享池：所有网站的 Service Worker 缓存都从这个池中分配

竞争关系：如果一个网站使用了大量缓存，其他网站的可用空间就会减少

单个网站的实际限制
虽然理论上没有硬性的单站限制，但实际上：

动态分配：Chrome 根据网站使用频率和重要性动态分配

LRU 策略：最少使用的缓存会被优先清理

无保证配额：单个网站无法保证能用到特定大小的缓存
缓存清理策略
当达到全局限制时，Chrome 会：

自动清理：基于 LRU（最近最少使用）算法

跨站清理：可能清理其他网站的缓存

无预警：不会通知网站缓存被清理
主动管理：定期清理旧缓存，避免被系统自动清理重要数据
